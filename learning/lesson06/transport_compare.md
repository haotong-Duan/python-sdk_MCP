# Compare stdio / HTTP

1. stdio 为什么适合本地 Agent？
    1. 零配置与免端口冲突：不需要分配 IP 或端口，完全不用担心端口被占用或本地防火墙拦截。
    2. 进程生命周期强绑定：Client（父进程）直接启动 Server（子进程），Client 退出或崩溃时，操作系统会自动关闭管道并回收子进程，不会留下孤立进程或僵尸服务。
    3. 极低延迟与高吞吐：直接通过内核管道（Pipe）在内存中传递数据，跳过了 TCP/IP 网络协议栈的封包、解包与握手开销。
    4. 天然的安全边界：不监听任何网络端口，意味着零网络攻击面，外部恶意程序无法直接通过网络探测或调用你的本地工具。

2. HTTP 为什么适合生产环境？
    1. 布式与远程部署：客户端（如云端 LLM 平台）与服务端（如数据库工具、内部 API 服务）可以部署在不同的物理机、容器或云服务商处。
    2. 弹性伸缩与高可用：支持通过负载均衡器（ALB、Nginx、Kubernetes Ingress）将请求分发给后端多个副本，实现水平扩容与无缝滚动更新。
    3. 成熟的安全与鉴权体系：可直接复用现有 HTTP 生态的安全标准，例如 HTTPS/TLS 加密传输、OAuth2/JWT 令牌鉴权、API Key 认证、WAF 防火墙及 IP 白名单。
    4. 可观测性与运维支持：方便无缝接入微服务基础设施，进行统一的日志收集、Prometheus 指标监控、OpenTelemetry 链路追踪以及 API 限流

3. 为什么 Protocol（定义消息的内含和形式） 不依赖 Transport（负责传输消息）？
    1. 关注点分离（Separation of Concerns）：Protocol 只关心“传递什么”（如：定义有哪些 Tool、输入参数格式、响应的 Schema，使用 JSON-RPC 2.0 标准格式）。Transport 只关心“怎么搬运”（如：是写入标准输出管道，还是发往一个 HTTP endpoint）。
    2. 无缝环境迁移（一次编写，到处部署）：开发者编写一次工具逻辑，在本地开发调试时通过 stdio 快速验证，生产上线时直接切到 HTTP/SSE 部署上云，核心业务代码一行都不需要修改。
    3. 未来的可扩展性：如果未来出现更高效的传输协议，只需要编写一个新的 Transport 适配器，原有的所有 MCP 客户端和服务端都可以直接兼容。

4. 为什么 MCP 可以跨语言？
因为 Python Client -> MCP Protocol -> Java MCP Server 中间没有python调用。
